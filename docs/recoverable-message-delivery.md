# 可恢复的消息投递与会话续接

状态：核心恢复链路已实现并完成本地验证；未执行生产发布或运行中应用验收。下文保留设计目标，实际覆盖与边界见第 9 节。范围：PiMac 原生客户端的消息投递、会话打开与恢复；不改写官方 T3 的执行历史，不自动重启 Server，不绕过授权或模型权限。

## 1. 目标与事实

用户点击发送后，必须能找回输入、知道处理到哪一步，并从中断点继续。恢复不是盲目重发，也不是悄悄换一个会话。

已核对当前实现：

- `AppModel.sendPrompt` 先清空 composer，再异步上传和提交；`pendingSentMessages` / `pendingQueuedMessages` 只保存在内存中。
- `AppModel.open` 清除本地待确认消息；现有 `WorkspaceModel` 草稿持久化只保护 composer，不能保护已经离开 composer 的输入。
- `T3DesktopClient.rpc` 把所有 RPC Failure 收敛成 `ClientError.rejected`，导致明确拒绝和未知结果难以区分。
- 排队输入可能通过 `queued-run.edit` 合并到已有消息；此时仅按新消息 ID 核验不能判断是否成功。
- 本次 14:02:33、14:02:42 的两个提交均报 `ProjectionStoreThreadNotFoundError`。这证明对应命令失败，但**不能仅凭此断言整段历史永久丢失或可安全重建同 ID 会话**。
- 安装版本中存在命令回执存储，但尚未核验公开查询入口、去重作用域、保留期、错误原子性和重放语义；不能据此承诺 exactly-once。

成功标准：切换页面、断线、退出或崩溃后，未交接输入仍可恢复；每次恢复都有明确结果或下一步。无法证明原上下文完整时，必须说明缺口。

## 2. 用户界面：一个恢复入口

输入框上方固定一条投递状态栏，不在每个气泡上重复堆按钮；展开后按输入顺序显示待处理项、具体原因和处理记录。状态栏预留稳定高度，检查中不挤动输入框与发送按钮。

| 情况 | 主提示 | 主操作 |
| --- | --- | --- |
| 离线、尚未发出 | 输入已保存在本机，连接恢复后可继续 | 检查并恢复 |
| 请求发出、回执未返回 | 正在核对是否收到，不会重复发送 | 检查并恢复 |
| 明确拒绝 | 发送失败：具体原因；原稿已保留 | 检查并恢复 |
| 会话不可用 | 当前会话无法续接，输入已保留 | 检查并恢复 |
| 已接收、未启动 | Server 已收到，等待启动 | 查看任务状态 |
| 本地保存失败 | 尚未发送，无法安全保存输入 | 重试保存 |

“检查并恢复”先执行只读核验，不直接生成新消息。核验完成后：

1. 原会话可用且已接收：关联原消息/运行，继续显示进度，不重发。
2. 原会话可用且符合安全重试条件：显示“继续发送”，保持原身份与原参数。
3. 原会话无法续接：显示迁移预览，以“在新会话继续”为唯一主操作，需要用户明确确认。
4. 仍不能确定：保留“结果待确认”，提供导出原稿及再次检查。不能以“刷新成功”冒充恢复成功。

低频操作放详情：复制/导出、退回草稿、忽略本地待处理项。忽略不等于取消 Server 运行；退回草稿不撤销已发请求，不覆盖现有 composer；主动重新发送已接收/未知结果的输入必须单独提示重复执行风险。

新输入可以继续编辑；同一会话存在未解决的投递时，默认暂停新的网络提交，避免不断追加“继续”使状态更乱。其他会话不受影响。

## 3. 持久化发件箱：先保存，再交接

新增 workspace 级 `MessageOutboxStore`，独立于标签页生命周期。它是未交接投递的单一事实来源；气泡、队列、侧栏和恢复栏均从它派生，不再各维护一组待确认副本。

### 数据结构

每个投递记录至少包含：

- 稳定 `submissionID`、`messageID`、目标 `threadID`、项目根目录及 Server 环境身份；不能仅按会变动的端口识别服务。
- 原始可编辑正文、实际 RPC 正文、附件清单、delivery、模型及 thinking/fast 等选项快照。
- 有序步骤及各步骤的稳定 `commandID`、冻结后的请求体/摘要、回执、远端消息/运行身份。一次逻辑输入可能涉及 project/create/upload/edit/dispatch，不能用一个总布尔值代表所有步骤。
- 创建时间、尝试次数、最后核验时间、结构化错误、状态版本、迁移来源及去向。
- 附件的本机持久文件、大小和摘要。受发件箱引用的附件不进入临时清理；缺失或损坏必须报错，不能默默只发文字。

正文和附件清单以原子事务提交。文件导入采用先暂存、校验，再发布引用；崩溃遗留的无引用暂存文件可稍后安全回收。目录/文件权限限制为当前用户；诊断日志不包含正文、凭据、附件内容或签名 URL。

### 发送顺序

1. 校验输入、模型、项目与附件；分配本次逻辑输入及必要步骤身份。
2. 写入持久化发件箱；失败则保留 composer，不发网络请求。
3. 仅在持久化成功后清除对应 composer 输入；异步结果绝不清空用户后来编辑的内容。
4. 每个变更请求发出前，持久化冻结请求及 `inFlight` 状态。确认前不能删除记录。
5. 权威回执/快照确认后交接显示身份；保留适当的已接收记录与迁移映射，避免客户端重启后重新投递。

composer 与 outbox 崩溃窗口可能留下同一份内容两处可见；使用交接 token 识别重复草稿，而不是冒险丢失输入。

发件箱损坏或读取失败不当作空发件箱。保留原文件，明确显示恢复失败；禁止在加载失败后写入空集合覆盖原记录。新建空会话的本地身份也须持久化，以便重启后定位未进入 Server 列表的投递。

## 4. 状态机与恢复策略

投递状态与执行状态分开：Server 接收 ≠ agent 启动 ≠ 任务完成。已执行失败不能通过自动重发用户输入来“修复”。

| 投递状态 | 含义 | 恢复行为 |
| --- | --- | --- |
| `saved` | 原稿可靠保存，尚未进入任何不确定变更步骤 | 检查环境后继续 |
| `preparing` | 正在准备项目/会话/附件 | 按步骤检查点继续 |
| `inFlight` | 已记录即将发出；崩溃后也可能实际未发 | 进入核验，不直接重发 |
| `unknown` | 可能已接收，但未拿到可靠证据 | 查回执/权威状态 |
| `rejected` | 收到明确失败，仍须区分可能的部分副作用 | 按错误及已完成步骤恢复 |
| `accepted` | 已确认对应消息/编辑及运行身份 | 交接到 Server 执行状态 |
| `needsMigration` | 原会话无法安全续接 | 用户确认迁移 |
| `dismissed` | 用户停止本地恢复，不表示远端取消 | 保留必要审计/去重信息 |

正常关闭、切换标签页、进程重启均不得清除非终态记录。重启时 `inFlight` 转入核验。网络恢复只自动做只读检查；长时间搁置的未发送输入需要用户确认继续，避免几天前的指令突然执行。

### 恢复决策顺序

1. 校验项目及 Server 环境身份；环境变更时不把旧命令自动发到新实例。
2. 查询权威会话详情和可用的命令回执，核对 `commandID`、`messageID`、run 及队列状态。
3. 查到原结果：标记 accepted，关联原运行；迟到的回执不能覆盖较新的迁移/取消决定。
4. 确认尚未请求，或经过核验的上游幂等契约允许相同冻结命令重放：从对应步骤继续。
5. 明确业务拒绝：显示实际错误；授权、模型、附件问题修复后再检查，不能自动改参数或降权限重试。
6. 会话不可用且无法安全重建：转迁移预览。
7. 证据不足：保留 unknown，提供安全导出。超时、列表暂时缺失、分页未包含、快照滞后均不等于“未收到”。

同一投递只能有一个恢复 worker；同一会话顺序处理有因果关系的变更。重连检查有退避和上限，用户点击不能创建并行重试。多次点击、多个窗口、旧回调均受持久状态版本/串行写入约束。

### 重试与队列合并的硬边界

- 重放相同命令必须保持原 `commandID` 和冻结请求内容；修正模型/文本等参数应是显式的新尝试，不复用旧 ID 偷改 payload。
- 新会话创建与首消息提交分别核验。创建响应丢失后，先找原会话，不再随机另建。
- 附件上传结果可核验/复用才复用；失败不丢失原文件。
- 当前 `queued-run.edit` 追加文本不是天然幂等。未核验版本/回执前，不能重新读取后再次拼接相同输入。
- 第一版恢复优先保证独立 `message.dispatch` 的完整闭环；若官方接口不能可靠提供合并操作的幂等与并发保护，应停止自动合并新输入，交由 Server 按独立队列消息处理。已有未知合并操作保留待核验，不能转为独立消息自动再发。
- 明确拒绝不必然意味着零副作用；错误分类和重试许可须按上游真实契约验证。

## 5. 会话不存在：恢复与迁移不能混淆

`ThreadNotFound` 先触发权威核验。列表有该 ID 但详情不可读时，报告状态不一致；不自动删除旧记录、插入数据库、重建同 ID 或重启整个服务。

只有上游明确支持、并且验证过语义的原身份续接才能叫“恢复原会话”。不支持时，走**新会话迁移**：

- 保留旧会话及本地记录，新建一次迁移计划，冻结目标新会话 ID；重复操作/崩溃恢复不得生成多份新会话。
- 预览迁移内容与缺口：可读取的对话、已知执行结果、未确认的输入、保留附件；显示来源及时间。
- 本地仅缓存到部分历史时，明确标注“仅恢复可读取内容”。不声称 Provider 隐藏上下文、工具权限、运行时进程、交互请求或完整执行状态已经恢复。
- 历史内容作为引用资料/上下文导入，不能把历史用户指令逐条再次执行。未确认旧操作单独标注，要求先核验外部副作用。
- 图片/文件只有仍可读取且获准携带时才迁移；附件缺失阻止相应输入发送，并提供重新选择。
- 迁移不自动回放审批、授权、付款、发布、命令行副作用或其他工具调用。
- 用户确认后才创建/发送；目标创建与投递照常经过持久化发件箱，失败后能续接同一迁移计划。
- 原投递与迁移投递保持对应关系。旧会话若迟到恢复/接收，提示冲突，不自动再执行两边，不抹除原始证据。

最差情况下，用户仍可导出全部**本机实际保存**的原稿、可用附件和恢复记录，再手动继续。恢复能力不等于承诺找回从未保存、已被外部删除或无法解密的数据。

## 6. 错误契约与代码落点

- `T3DesktopClient.swift`：保留 RPC Failure 的结构化错误链、失败阶段及请求是否可能已发；区分授权/业务拒绝/传输未知/无效响应。安全文案不能直接展示可能含凭据的上游原始文本。
- 新增 `MessageOutboxStore`：带版本的可靠持久化、原子交接、附件引用、损坏保护、稳定身份；不存另一份权威 Server 历史。
- 新增 `MessageRecoveryCoordinator`：串行步骤、只读核验、条件重试、退避和迁移计划；通过真实客户端接口执行，不让 View 拼装恢复命令。
- `AppModel.swift`：先保存后清空，读取发件箱派生气泡/队列；切换/打开/断开不再删除未交接输入；把原稿送回 composer 时保留现有草稿。
- `WorkspaceModel.swift`：持有共享发件箱与恢复 coordinator，恢复入口能找到从未成功创建的会话；不依赖当前选中标签页存活。
- `ContentView.swift`：统一恢复栏、详情与迁移确认；逐消息显示事实状态，避免所有错误都叫未确认。
- 临时文件清理与 development reload：保护发件箱引用文件、恢复写入及未确认操作；不得自动释放其他任务的屏障。

不为恢复功能额外限制 T3 Provider/模型/工具；沿用现有官方认证及权限。

## 7. 必须通过的验收

1. 首条含图片发送成功：立即可见，最终按原 ID 交接，只创建一个会话/运行。
2. 本地保存失败/磁盘满：不发请求，composer 完整；损坏文件保留且不覆盖。
3. 保存后崩溃、创建响应丢失、提交响应丢失：重启后保留原稿与身份；已接受的操作不再执行。
4. `ThreadNotFound`：显示具体原因，有恢复入口；无法续接时迁移需确认，原记录保留。
5. 断线后点多次、自动重连、切换标签页：不产生并行变更或丢失输入，其他会话正常。
6. 附件丢失/损坏：不默默省略；可重选，原文本仍在。
7. 授权过期/模型不可用：修复配置后能继续，不绕过权限或自动换模型。
8. queued-run.edit 超时且可能已生效：不重复拼接，不自动再发独立消息。
9. 快照滞后、分页缺失、旧回调迟到、迁移中旧回执到达：不错误认定未接收，不重复执行。
10. 新环境/不同项目：不跨身份投递；用户原 composer 不被恢复动作覆盖。
11. 迁移创建或首消息再次失败：续接同一目标，无多份新会话；上下文缺口可见。
12. 已接收后执行失败：继续观察/恢复原运行，而非自动重发原用户指令。
13. 原生同数据/尺寸/主题 before/after；覆盖初始、检查中、核验完成/迁移确认，恢复栏无布局跳动。

验证层次：纯状态机与持久化故障测试 + 隔离的真实 T3 接口/进程断连测试 + 原生组件交互与截图；不能用只 mock JSON 的绿灯声称已经证明上游去重与崩溃恢复。所有真实服务测试使用独立测试数据目录，不操作当前正在工作的 Server 或业务数据库。

## 8. 交付顺序与停止条件

1. 核实官方错误、回执与重放契约，补足恢复判据；任何未知契约禁止推测性自动重试。
2. 交付持久化发件箱、先保存后提交、结构化错误、统一检查/原稿恢复入口，完成断线/重启闭环。
3. 交付原会话核验与受契约保障的重试，再交付明确确认的新会话迁移。
4. 完成关键失败注入与真实原生前后对比，再接入正常发布门禁。

每阶段单独报告已实现、已验证及不能恢复的边界。第一阶段不能宣称完整迁移已完成；设计文档不等于已上线能力。

## 9. 当前实现与验证

### 已实现

- `MessageOutbox.swift`：共享持久发件箱、附件私有副本与摘要校验、原子清单、重启后的未知状态恢复、损坏保护与重新读取、暂时保存失败后的重试、原稿/附件导出。
- 同文件的 `MessageRecoveryCoordinator`：按线程串行核验和投递，绑定官方 `server.getConfig.environment.environmentId`；从冻结的创建/投递请求继续，保持原 commandID；不按正文或快照暂时缺失判断“未收到”。
- `T3DesktopClient.swift`：保留结构化 RPC 类型，兼容官方 `Schema.Defect` 的 `name` 编码；HTTP 404 与传输失败分开处理。错误类型不等于可以自动重发。
- `AppModel.swift` / `WorkspaceModel.swift`：发送前先保存，成功保存才清空 composer；气泡和待确认队列从发件箱派生；关闭/重开标签或客户端重建仍能在侧栏找到投递；迁移时同步保存未改动的新草稿归属。
- `MessageRecoveryBar.swift`：统一检查入口、受保护的继续发送、迁移预览和确认、原稿取回、文字复制、附件导出、保存故障恢复、保留记录并停止恢复。取回原稿不覆盖当前新输入；其备份持续保留到新提交原子接管。
- 新会话迁移的来源映射与目标投递一次提交，重复调用复用目标；旧会话迟到的确认会把目标标为冲突，阻止继续恢复并要求人工核验。
- 新排队输入改为独立 Server 消息，不再自动拼接 `queued-run.edit`，避免未知结果再次追加正文。

### 上游契约依据

核对了固定上游的 `orchestration-v2/Orchestrator.ts` 与 `EventSink.ts`：官方读取原 commandID 回执，校验所属线程，已接受命令返回原结果；接收事件、投影、回执和 effect outbox 在事务中交接。这里只对 `thread.create` 和 `message.dispatch` 使用同一冻结命令重放，不扩大到有独立副作用的控制命令。明确拒绝后的修正输入以新的用户提交处理，不偷偷改变原命令的参数。

### 有效验证
